# 设计：基于退化仿真的预测性维护

日期：2026-07-17
状态：已获用户批准

## 背景与目标

当前 `MachineDataGenerator` 每 10 秒生成无状态的随机传感器数据（基线 × 时段负载 × 噪声 + 3% 瞬时异常），设备不会真正老化，故障无前兆，无法支撑预测性维护演示。

目标：引入可靠性工程的科学模型（Gamma 式退化累积、故障模式症状映射、ISO 10816 振动阈值），让数据具有"渐进退化 → 前兆 → 故障 → 维修恢复"的真实轨迹，并在此数据基础上实现**健康度评分**与**剩余寿命预测（RUL）**两个 App 功能。

范围决策（已确认）：
- 数据路线：A 方案 —— Java 内嵌退化仿真，不引入 Python sidecar，不做数据集回放
- 老化节奏：加速老化，完整周期（健康→告警）约 2 小时，适合现场演示
- 设备：保持现有 18 台真实型号，补充真实额定技术参数，不新增设备
- App 功能：健康度评分 + RUL 预测；**不做**预防性工单自动推荐

## 第 1 部分：设备额定参数

`Equipment` 实体新增可空字段（兼容旧数据）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `ratedSpindleSpeed` | Double | 额定主轴转速 rpm |
| `ratedPower` | Double | 额定功率 kW |
| `ratedCurrent` | Double | 额定电流 A |
| `normalTempMax` | Double | 正常运行温度上限 °C |

- `DataInitializer` 按公开规格表为 18 台设备逐台填值（如 CK6150 约 7.5kW/1400rpm，VMC850 主电机约 11kW/8000rpm，实施时逐台核对）
- 已存在的数据库记录通过启动时补齐逻辑填充（额定值为空时按型号补写）
- `MachineDataGenerator` 改为读取每台设备额定值做基线，删除现有"按设备名猜基线"逻辑（现 46-54 行）

## 第 2 部分：退化仿真引擎

### 新实体 `EquipmentHealth`（每台设备一行，持久化）

| 字段 | 范围 | 退化含义 | 主要症状 |
|------|------|---------|---------|
| `bearingWear` | 0~1 | 轴承磨损 | 振动超线性上升；磨损 >0.5 后温度跟涨 |
| `coolingDecay` | 0~1 | 冷却系统衰减 | 仅温度上升 |
| `toolWear` | 0~1 | 刀具磨损 | 电流/功率上升 + 振动小幅上升 |

### 每 10 秒生成逻辑（重构 `MachineDataGenerator`）

1. **退化累积**：`磨损 += max(0, N(μ·load, σ)) × 加速系数`——单调递增的随机增量（Gamma 过程的简化近似），高负载时段退化快，夜间几乎不退化。各设备退化速率带随机差异
2. **症状映射**：传感器读数 = 额定基线 × 时段负载 × f(磨损状态) × 噪声；f 按上表故障模式因果规则实现（参照 AI4I 2020 数据集的生成规则思想）
3. **阈值判定**：振动阈值采用 ISO 10816 分区值；温度按 `normalTempMax + 裕度`；替换现有硬编码阈值
4. **维修闭环**：`WorkOrderService` 完成工单时按故障类别复位对应磨损量（机械故障→bearingWear，温控故障→coolingDecay，电气/传动→toolWear 等映射），设备数据可见地恢复正常
5. **启动错峰**：首次初始化 18 台设备的磨损量随机分布（大部分健康、数台中度退化、1-2 台接近告警），演示开箱即有内容
6. **加速系数**：`application.yml` 配置项（`app.simulation.acceleration`），默认值使完整退化周期约 2 小时

## 第 3 部分：健康度评分

- 新增 `HealthService`、`HealthController`
- **评分只用可观测遥测数据，不读隐藏磨损量**：取近 10 分钟 `MachineData` 均值，计算相对额定基线的偏离度，加权扣分：振动 40% + 温度 30% + 电流/功率 30%，得 0-100 分。该算法对未来真实传感器数据同样成立
- API：
  - `GET /api/health/scores` —— 全部设备健康分列表（含排序）
  - `GET /api/health/{equipmentId}` —— 单台详情：总分、各因子扣分明细、趋势数据点、RUL
- Android：监控页设备卡片加健康分色环（≥80 绿 / 60-79 黄 / <60 红），支持按健康度排序；详情页显示因子扣分明细

## 第 4 部分：剩余寿命预测（RUL）

- 在 `HealthService` 内实现：取近 30 分钟主导退化指标（偏离最严重的传感器），线性回归求斜率，外推至告警阈值，输出"预计 X 小时后达到告警阈值"
- 趋势平稳（斜率≈0 或负）时返回"暂无退化趋势"
- 不用机器学习——回归外推可解释、零依赖，因数据确有退化趋势而有效
- Android 详情页：趋势折线 + RUL 预测文案

## 错误处理

- 额定参数缺失的设备：仿真回退到型号类别默认基线；健康评分标记"数据不足"
- 遥测数据不足 10 分钟：健康分返回空并提示积累中；RUL 同理
- 磨损量越界防护：clamp 到 [0,1]

## 测试

- 单元测试：退化数学（单调性、负载相关性、复位、clamp 边界）、健康评分（权重、边界分值）、RUL 回归外推（上升/平稳/数据不足三情形）
- 集成测试：health 两个 API 端点
- Android 端编译验证（无 Android Studio 环境，UI 由用户实机验证）

## 不做的事

- 预防性工单自动推荐（用户明确不选）
- Python sidecar / ProgPy / 数据集回放
- 新增设备数量
- 机器学习模型
